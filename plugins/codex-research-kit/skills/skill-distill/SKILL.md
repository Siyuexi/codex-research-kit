# distill — turn recurring interactions into draft skills, and keep existing skills honest

`distill` is a **meta-skill** with two jobs that share the same scan:

1. **New** — watch the tasks you already ask Codex to do, look for repetition,
   propose new skills that would let future-you ask the same thing in fewer
   words. Produces disabled skill drafts under `~/.codex/skills/<slug>/SKILL.md`.
2. **Revise** — audit the skills you already wrote against
   how they actually got used. Flag description drift, constitution
   violations, user complaints about a step, and dead templates. Produces a
   **suggestion list** in the report — never an automatic edit. You apply
   suggestions one at a time by asking Codex to use `$distill apply <id>`.

Both outputs feed the same dated report at `~/.codex/distill/archive/YYYY-MM-DD.md`,
so one distill run answers both "what new skills should I write?" and
"are my existing skills aging well?".

> **Why disabled-by-default.** A skill that the model loads automatically is a
> chunk of your attention budget. If `distill` enabled drafts on its own, a
> bad draft would silently degrade every future session. The cost of one extra
> manual edit per skill is much smaller than the cost of one bad auto-enabled
> skill.

---

## When to use

- The user explicitly says "distill" / "distill the last few days" / "总结一下我最近问你的事情" / "看看有什么能做成 skill" / "看看你被反复问什么".
- The user explicitly mentions `$distill` or asks to distill.
- The user explicitly asks to run distill now.
- You proactively notice that the user has asked for the same kind of thing
  3+ times in this session and they sound mildly annoyed. (Suggest distilling
  with one line; do not just start scanning.)

## When NOT to use

- The user asks "summarize this conversation" — that is **codex-memory** or a direct response, not distill. Distill is cross-session pattern mining.
- The user asks for a specific past task ("what did we decide about X last
  Tuesday?") — use `codex-memory search` / `recall`.
- The user wants to *write* a skill they've already designed in their head —
  go straight to the `skill-creator` skill or just write the file.
- A single ongoing project's status — that belongs in the project's own log
  (e.g., research-workflow `log/`), not in a cross-project distill report.

## Section 1 — The Distill Constitution (C-D1 ~ C-D6)

These are non-negotiable. The whole point of `distill` is that future-you
trusts the drafts enough to read them — if any of these rules slip, the
drafts become noise and the skill self-defeats.

### C-D1. Drafts are disabled until the user flips the bit

Every generated `SKILL.md` MUST contain both `status: draft` and
`disabled: true` in frontmatter. The skill description MUST begin with
`[DRAFT — generated by distill on YYYY-MM-DD, not yet approved by user]`.

**Why:** auto-enabled drafts pollute every future session's skill list. The
manual review step is the only thing that keeps draft quality honest.

**How to apply:** never edit `disabled: true` to `false` inside this skill,
even if a candidate looks obviously correct. Promotion is a human act.

### C-D2. Frequency floor + signal weight

Only propose a draft if `score = frequency + 2 × signal_weight >= 3`, where:
- `frequency` = distinct sessions in which the pattern appears,
- `signal_weight` = explicit repetition phrases ("又是", "every time", "stop doing", "keep doing", "上次也", "同样").

Borderline candidates (`score == 2` with at least one signal) go in a
separate `borderline:` list in the report — surfaced for the user, but **not
drafted as files**.

**Why:** a one-off task isn't a skill; it's a task. The 2× weight on language
signals catches "this happened twice but the user is clearly annoyed" — which
is just as valid a trigger as raw count.

**How to apply:** the scanner sub-agent computes this score (see
`templates/scanner-prompt.md.template`). Do not relax the threshold without
the user asking for it.

### C-D3. Evidence is mandatory — no synthesized quotes

Each draft and each report entry MUST include ≥ 2 verbatim user quotes from
different sessions (or, if a long single session contains multiple genuine
restatements, ≥ 2 quotes from that session, flagged in `notes`). Quotes are
truncated to ≤ 200 chars, never paraphrased.

**Why:** without evidence, "distill" becomes "Codex makes things up about
what the user wants." With evidence, the user can verify or reject each
candidate in seconds.

**How to apply:** if the scanner returns a candidate with fewer than 2
quotes, drop it rather than weakening this rule.

### C-D4. Don't propose what already exists

The scanner is given the user's currently-installed skill list (see
`templates/scanner-prompt.md.template`, "Excluded" section). It must skip
patterns already covered. If a pattern *extends* an existing skill (e.g.
"a research-workflow sub-skill for X"), the candidate is allowed but must carry
`extends: <skill-name>` so the human reviewer can decide to merge instead of
fork.

**Why:** the harm of duplicating an existing skill is bigger than the cost of
occasionally missing a worth-distilling pattern. Skill duplication causes
description-match ambiguity and silently degrades skill triggering.

**How to apply:** when in doubt, treat the existing skill as authoritative
and drop the candidate.

### C-D5. The main agent does not read raw transcripts

The main Codex session dispatches an isolated Codex sub-agent to read `*.jsonl`
and return only the structured JSON report.
Transcripts are large; reading them in the main session would burn the
attention budget that the user expects to spend on real work.

**Why:** a single day's transcripts across all projects can be hundreds of
thousands of tokens. Sub-agent isolation is the only way to keep this skill
cheap to invoke.

**How to apply:** never inline `Read` of a `*.jsonl` from the main session.
Always go through the Codex sub-agent tool with the scanner prompt template.

### C-D6. State is the source of truth for "what's been seen"

`~/.codex/distill/state.json` records `last_run` (ISO 8601), all `runs`
(historical metadata), and `distilled_slugs` / `dismissed_slugs`. Every run
- reads `last_run` to default the scan window,
- appends to `runs`,
- updates `distilled_slugs` with the slugs of drafts written this run,
- writes the new `last_run` timestamp **only after** all drafts and the
  report file are on disk (so a crash leaves the window unchanged).

**Why:** without this file, every run re-distills everything and the user
sees the same drafts repeatedly. With it, the next run picks up exactly
where this one stopped.

**How to apply:** see Section 4 for the exact update sequence.

### C-D7. Revisions are suggested, never auto-applied

The revision audit (Step 4.5) produces a list of suggested edits to existing
user-authored skills. The skill MUST NOT call `Edit` on a target
file during a normal distill run, no matter how confident the suggestion
looks. Each suggestion is written to the report only. Applying a suggestion
is a separate explicit action (`$distill apply <id>`) that re-reads the
suggestion, asks the user to confirm, and only then performs the edit.

**Why:** the skills being audited are infrastructure the user relies on
session after session. A bad auto-edit to e.g. `research-workflow/SKILL.md`
silently degrades every future research session. Suggestions are cheap —
the user can scan a list of 5 in 30 seconds and dismiss the noise. Bad
auto-edits are expensive — the user might not notice the regression for
weeks. This rule mirrors C-D1 (drafts disabled by default) for the same
reason: the cost of a manual approval click is much lower than the cost of
a silent infra regression.

**How to apply:**
- The reviser sub-agent (`templates/reviser-prompt.md.template`) returns
  suggestions; the main agent writes them into the report under the
  `## Skill revision suggestions` section.
- Never use `Edit` / `Write` on any path matching `~/.codex/skills/*/` or
  unsupported `~/.codex/commands/*` files during scan / report steps.
- The only path that mutates target files is `$distill apply <id>` (Section 7),
  and that path MUST: read the suggestion's `suggested_diff.before` and
  `.after`, show them to the user, wait for confirmation, then `Edit` with
  `before` as `old_string` and `after` as `new_string`. If the `before`
  text no longer exists in the file (because the user already edited it),
  report the drift and stop — do not try to guess where the edit should go.

## Section 2 — Inputs and triggers

`distill` has two equivalent entry points. The behavior is identical; only
the wrapper differs.

### 2a. Natural-language trigger

The user says something like "distill my interactions", "总结一下我最近问你的事情",
"看看有什么值得做成 skill", "what have I been asking you for a lot lately". You
match this skill's description and load it.

### 2b. Skill mention

The user explicitly mentions `$distill` (optionally with args) or selects the
`distill` alias skill from `/skills`. Codex CLI does not load user-defined
slash commands from `~/.codex/commands`; this kit uses skills as the active
entry surface. See Section 7.

### 2c. Manual only

Do not install cron, loop, or lifecycle-hook wrappers for this skill. The user
may run `$distill` explicitly, but automatic distillation is intentionally out
of scope because session mining writes durable skill artifacts.

### Arguments (all optional)

| Arg              | Default                                     | Meaning                                                                  |
|------------------|---------------------------------------------|--------------------------------------------------------------------------|
| `--days N`       | (unset — fall back to state.json)           | Scan the last N days instead of "since last run"                         |
| `--since ISO`    | (unset)                                     | Explicit lower bound, e.g. `--since 2026-05-15T00:00:00Z`                |
| `--project TEXT` | all projects                                | Restrict to sessions whose `cwd` contains TEXT                           |
| `--dry-run`      | false                                       | Run scanner, emit report, **skip** writing skill drafts and state update |
| `--min-score N`  | 3                                           | Override the C-D2 threshold (be honest with yourself if you lower it)    |

were originally typed into Codex, but nothing from outside the

## Section 4 — Workflow

This is the procedure to run when triggered. Each step is one or two tool
calls.

### Step 0 — Ensure state file exists

Check `~/.codex/distill/state.json`. If missing, copy
`templates/state.json.template` to that path. Read it; remember
`last_run` (may be `null`) and `distilled_slugs`.

### Step 1 — Resolve the scan window and list sessions

Run:

```
python3 ~/.codex/skills/skill-distill/bin/list-sessions.py \
    [--days N | --since ISO | --project SLUG] \
    --exclude-current-session $CURRENT_SESSION_ID \
    --json
```

If no `--days` / `--since` was passed, the script defaults to
`state.json#last_run`, or 1 day if state is empty.

The script returns a JSON array of `{mtime, project, path, lines, session_id, cwd, title}`.
If empty, write a "nothing to distill" report and stop (Step 6).

If the current session id is available, pass it via `--exclude-current-session`.
Excluding it prevents the in-flight distill conversation from polluting its own
scan.

### Step 2 — Dispatch the scanner sub-agent

Load `templates/scanner-prompt.md.template`. Substitute:
- `{{SINCE_ISO}}` ← resolved window start
- `{{JSONL_PATHS}}` ← newline-joined paths from Step 1
- `{{ALREADY_DISTILLED}}` ← newline-joined `state.json#distilled_slugs` ∪ `dismissed_slugs`

Spawn one Codex sub-agent with a prompt built from the filled template. The
sub-agent is the scanner and must return only the JSON schema documented in
the template.

The sub-agent reads jsonl in isolation and returns the JSON schema documented
in the template. Parse it. If it fails to parse, log the failure to the
report under "Scanner errors" and stop without updating state.

**Do not** call multiple scanners in parallel for the same window — they
would produce contradictory dedup decisions. One scanner per window.

### Step 3 — Filter against installed skills (defense in depth)

The scanner already excludes installed skills, but the list of installed
skills can change between when the template was written and when the user
runs distill. So:

For each candidate slug, check `~/.codex/skills/<slug>/SKILL.md`. If it
exists, drop the candidate and log "skipped — already installed: <slug>" in
the report. This is cheap and catches drift.

### Step 4 — Write skill drafts

For each surviving candidate:

1. Compute the target directory: `~/.codex/skills/<slug>/`.
2. If it already exists, append a numeric suffix (`<slug>-2`, `<slug>-3`) and
   log the rename.
3. `mkdir -p` the directory.
4. Render `templates/skill-draft.SKILL.md.template` with the candidate's
   fields and write to `<dir>/SKILL.md`.
5. Verify the file starts with `---\n` and contains both `disabled: true`
   and `status: draft`. If not, delete the file and log an error. (C-D1
   guardrail.)

Borderline candidates (Section 1 C-D2) are NOT written as files — they only
appear in the report.

### Step 4.5 — Audit existing user-authored skills for revisions

This step runs **in parallel with Step 4** when possible (separate sub-agent,
no dependency on Step 4 results). It produces revision suggestions for
existing skills you already use.

1. Run:
   ```
   python3 ~/.codex/skills/skill-distill/bin/list-user-skills.py \
       --with-usage <path-to-sessions.json-from-Step-1> \
       --top 5 \
       --json
   ```
   This returns the top-5 most-referenced user-authored files in the scan
   window. "Top 5" is a deliberate cap: auditing every user file every run
   is expensive and dilutes signal. The audit rotates through busy files;
   unused ones bubble up only when they get used.

   If the list is empty (no user-authored skill was referenced in the
   window), skip this step entirely and note "no revision audit this run"
   in the report.

2. Load `templates/reviser-prompt.md.template`. Substitute:
   - `{{SINCE_ISO}}` ← same window start as the new-skill scanner
   - `{{JSONL_PATHS}}` ← same paths as Step 2
   - `{{TARGET_FILES_JSON}}` ← the JSON from step 1 above
   - `{{ALREADY_SUGGESTED}}` ← `state.json#suggestion_fingerprints` joined by newlines

3. Spawn a separate Codex sub-agent with the filled reviser template.

   Run this in parallel with Step 4 (drafting). They write to disjoint
   places — Step 4 writes new skill files, Step 4.5 only returns JSON.
   No race conditions.

4. Parse the returned JSON. For each suggestion:
   - Compute its `fingerprint` if the sub-agent didn't supply one
     (`sha1(target_path + section + signal_type)[:12]` is fine).
   - **Verify** `suggested_diff.before` actually appears in the file
     (substring match). If it doesn't, drop the suggestion and log a
     "stale-diff" warning — the file moved since the sub-agent read it.
   - Drop anything matching a fingerprint in
     `state.json#suggestion_fingerprints` or
     `state.json#dismissed_suggestion_fingerprints`.

5. Hold the surviving suggestions in memory for Step 5 (report writing).
   **Do not edit any file** in this step. C-D7 is the load-bearing rule.

### Step 5 — Write the report (and the suggestion sidecar)

Render `templates/daily-report.md.template` to
`~/.codex/distill/archive/YYYY-MM-DD.md` (using today's local date).
If the file already exists (you ran distill twice today), append a
`## Run at HH:MM:SS` divider and write below it — do not overwrite.

**Also write the full suggestion JSON** to
`~/.codex/distill/archive/YYYY-MM-DD.suggestions.json` (one file per day,
overwrite-then-merge: if it exists from an earlier run today, load it,
extend with this run's suggestions deduped on `id`, write back). This is
the machine-readable record that `$distill apply <id>` and
`$distill dismiss-suggestion <id>` read from. The markdown report is for
humans; the sidecar JSON is for the apply path.

### Step 6 — Update state

Only now, after files are on disk:

```json
{
  "last_run": "<scan window end ISO, UTC>",
  "runs": [
    ...previous runs,
    {
      "timestamp": "...",
      "since": "...",
      "until": "...",
      "drafts_written": ["<slug>", ...],
      "suggestions_written": ["<fingerprint>", ...],
      "report_path": "~/.codex/distill/archive/YYYY-MM-DD.md"
    }
  ],
  "distilled_slugs": [...previous, ...drafts_written],
  "dismissed_slugs": [...unchanged],
  "suggestion_fingerprints": [...previous, ...suggestions_written],
  "dismissed_suggestion_fingerprints": [...unchanged],
  "applied_suggestion_fingerprints": [...unchanged]
}
```

The three suggestion-related fields work like the slug fields, but for
revision audit (C-D7): `suggestion_fingerprints` is the union of every
suggestion the user has seen (so Step 4.5 doesn't re-emit them);
`dismissed_*` is for ones the user explicitly rejected via `$distill dismiss-suggestion <id>`;
`applied_*` is for ones the user accepted via `$distill apply <id>` —
applied suggestions stay in the dedup set so the same audit doesn't re-fire.

Write atomically: write to `state.json.tmp`, then rename to `state.json`.

### Step 7 — Report to the user

Output to the main session:
- One sentence: "Scanned N sessions across M projects, wrote K drafts and S revision suggestions."
- A bullet list of the drafted slugs with their score and one-line title.
- A second bullet list of revision suggestions: `<id>` → `<target_name>` :
  `<one-line summary>` (severity).
- The path to the full report.
- A reminder: "Drafts are disabled — open the SKILL.md and remove `disabled: true`
  to enable. Suggestions are NOT applied automatically — ask Codex to run `$distill apply <id>`
  after reading the diff in the report."

Keep this output ≤ 20 lines. The full report is on disk for browsing.

## Section 5 — Promoting / dismissing drafts and applying / dismissing suggestions

After a `distill` run there are **two** queues to triage: new-skill drafts
and revision suggestions. They have parallel verbs.

### Drafts (new skills)

1. **Promote**: edit the file, remove `status: draft` and `disabled: true`,
   tighten the description, then it's live.
2. **Dismiss permanently**: delete the file AND add the slug to
   `state.json#dismissed_slugs`. Without the dismissal, future scans will
   re-propose it.
3. **Leave it**: do nothing. The file stays disabled, future scans skip it
   because the slug is in `distilled_slugs`.

### Suggestions (edits to existing skills)

1. **Apply**: `$distill apply <id>` — read the suggestion's
   `suggested_diff.before` + `.after`, show the user, wait for explicit
   confirmation, `Edit` the file, add `<fingerprint>` to
   `state.json#applied_suggestion_fingerprints`.
2. **Dismiss**: `$distill dismiss-suggestion <id>` — add `<fingerprint>` to
   `state.json#dismissed_suggestion_fingerprints` (so future audits skip
   the same finding).
3. **Leave it**: do nothing. The fingerprint is in `suggestion_fingerprints`
   so it won't be re-emitted, but future audits can surface *different*
   issues on the same file.

You (Codex) can help with any of these when the user asks ("promote
distill-foo" / "apply rev-research-survey-3" / "dismiss-suggestion rev-research-survey-3").
The `$distill` skill alias (Section 7) exposes them.

## Section 6 — Anti-patterns

### AP-1. Writing drafts that look ready to ship

Drafts are **proposals**, not finished skills. They should have placeholders,
TODO markers, and questions for the human. A draft that reads like a
polished skill encourages the human to skim and miss errors.

**Correct shape:** "When to use: {{WHEN_TO_USE — fill in based on the
evidence quotes above}}".

### AP-2. Re-proposing the same pattern every run

If you find yourself listing the same candidate slug across multiple runs,
it means `state.json` is not being updated or the user keeps deleting drafts
without dismissing them. Surface this to the user: "I see `<slug>` for the
3rd time — should I dismiss it permanently?".

### AP-3. Treating frequency as the only signal

Three identical "find the file that does X" requests across three projects
are NOT a skill — they're three independent searches that happened to share
shape. The scanner's "shape" field (inputs / steps / outputs) is the filter:
if you cannot describe the procedure in 3 steps, it isn't a skill.

### AP-4. Distilling research-workflow sub-projects as standalone skills

Anything that smells like "research workflow" / "literature survey" /
"review my project" should `extends: research-workflow` (or a sub-skill) and be
flagged for **merging** into that family rather than birthed as a sibling.
The research-workflow family already covers the research lifecycle; new
top-level skills there fragment the routing table.

### AP-5. Mixing project-specific and global patterns

A pattern that only appears under one project `cwd` is
either project-local (belongs in that project's `AGENTS.md`) or a global
skill in disguise. The scanner reports the project distribution of evidence
in the `evidence` array. If all quotes are from one project, prefer
proposing a AGENTS.md addition over a global skill — note this in the
candidate's `notes` field.

### AP-6. Auto-applying a "high-confidence" revision suggestion

The reviser sub-agent will sometimes return a suggestion that looks
obviously correct — typo fix, dead template removal, a description rewording
that's clearly an improvement. C-D7 still applies. The skill MUST NOT call
`Edit` on the target file during a scan run, ever. The cost of a wrong auto-
edit on a critical infra file (e.g. `research-workflow/SKILL.md`) outweighs the
convenience of skipping one `$distill apply <id>` call. If you find yourself
arguing "but this one is so obviously right" — that's exactly when this
guardrail is doing its job. Write the suggestion to the report; let the
user say "apply".

## Section 7 — The `$distill` skill alias

The `distill` alias skill accepts the same argument shapes in natural language
or explicit `$distill ...` mentions:

- `$distill` — default run (since last) — scan + draft + audit + report
- `$distill --days 7` — fixed window
- `$distill --dry-run` — scan and report without writing drafts or updating state
- `$distill promote <slug>` — enable draft `<slug>` (remove `disabled: true`, `status: draft`)
- `$distill dismiss <slug>` — delete the draft file, add `<slug>` to `dismissed_slugs`
- `$distill revisions` — print the latest report's revision-suggestions section
- `$distill apply <id>` — apply one revision suggestion (with explicit user confirm)
- `$distill dismiss-suggestion <id>` — record permanent rejection of one suggestion
- `$distill status` — print `state.json` summary, disabled drafts, pending suggestion count

The skill body (you, when invoked) is what executes the action.

### How `$distill apply <id>` works

1. Read `state.json#runs[-1].suggestions_written` to find the run that
   emitted `<id>`. Read that report's revision section to load the
   suggestion record (or read from a sidecar JSON if one was written —
   see Section 8 failure modes).
2. If the record's `target_path` does not exist, abort and tell the user.
3. Show the user: target file, `section`, `severity`, `confidence`,
   `summary`, and the `before` / `after` diff (verbatim).
4. Wait for the user to confirm ("yes" / "apply" / "go ahead"). If they
   say no, treat as `$distill dismiss-suggestion <id>` and stop.
5. On confirm, call `Edit` with `old_string=before`, `new_string=after`.
   If `Edit` fails because `before` is no longer unique in the file
   (because the user edited it after the audit), tell the user and stop —
   do NOT call `Edit` with `replace_all`.
6. Append `<fingerprint>` to `state.json#applied_suggestion_fingerprints`
   atomically.

## Section 8 — Failure modes and recovery

| Failure                                       | Recovery                                                                                     |
|-----------------------------------------------|----------------------------------------------------------------------------------------------|
| `state.json` corrupt JSON                     | Move to `state.json.bak.<ts>`, recreate from template, log to report, ask user before re-running |
| Scanner returns malformed JSON                | Save raw output to `~/.codex/distill/archive/YYYY-MM-DD.scanner-error.txt`, do not update state |
| `mkdir` fails (slug collides with existing skill not caught in Step 3) | Skip that candidate, log to report, continue with the rest                                   |
| Scan window has zero sessions                 | Write a "nothing to distill" report, still update `last_run` so the empty window isn't re-scanned next time |
| User interrupts mid-run                       | State is only written in Step 6, so an interrupted run leaves no state change — safe to re-run |
| Reviser sub-agent returns malformed JSON      | Skip the revision audit for this run, log to report, continue with new-skill drafts (the two halves are independent) |
| Suggestion sidecar JSON missing on `apply`    | Tell the user: re-run `$distill` to regenerate, or read the markdown report and apply manually with Edit |
| `Edit` fails on apply because `before` text drifted | C-D7 requires NOT using `replace_all` — report the drift, ask the user to re-run distill so the suggestion regenerates against the current file |
